## 1. 结论先行

**可行，而且比听起来容易 —— 但"拼接"的正确做法不是"两支 mp4 接起来"。**

| 做法 | 后果 |
|---|---|
| ❌ 各渲各的 mp4，然后 `ffmpeg concat` | 两边是**两套 sRGB / 色调映射 / 泛光 / 颗粒**实现，接缝一定看得出来；`verify` 也失去意义 |
| ✅ Three.js 的画面作为**一个图层**进 anim 的合成器 | 同一套后处理、同一条 NV12 推流、同一个 `verify`；接缝退化成一次普通镜头切换。**最终仍然是"一部片子、一次出片"** |

而且有一条**判据**必须先过（§8）：**你到底需不需要"导入模型"**。
不需要（几何能用数学描述）→ 引擎**已经有**一条真 3D 路线（raymarch），加依赖的性价比很可能不划算。
需要（`.glb`/`.gltf`、捏出来的具体东西）→ 才值得做本文档这件事。

---

## 2. 为什么可行：三个已经就位的前提

1. **两边都是 Chrome 里的 WebGL2。** `anim` 的场景就是画进一张 render target（`ctx.out`），
   Three.js 也是往 GL 里画 —— 它们在同一张画布上碰面，不存在"两个渲染器没法合"的问题。
2. **引擎本来就是逐帧离线渲染。** 不需要实时 60fps，每帧多花 10ms 做一次拷贝完全可以接受。
3. **后处理链在合成之后统一施加**（泛光/光晕/颗粒/暗角/色调/shoulder）。
   这就是"看起来像同一支片子"的关键：Three.js 的画面只要进了合成器，就自动吃到和别的镜头**完全同一套调色**。

## 3. 架构：一条 Three.js 镜头怎么走完整条链

引擎现在的路（我读过 `src/core/engine.js` / `gl.js` 确认）：

```
scene.render(ctx)
  → gl.clear(ctx.out) + lines / text / Pass   ← ctx.out 是一张 render target
  → comp.draw(...)                             ← 图层合成（Compositor）
  → 后处理链（post.js：bloom / halation / grain / vignette / ca / shoulder）
  → readNV12() → WebSocket → Node → ffmpeg
```

要插进去的东西（**新文件**，建议 `src/core/three-bridge.js`）：

```
three 镜头：
  THREE.WebGLRenderer.render(scene, camera)    ← 渲到自己的 offscreen canvas
  → gl.texImage2D(..., canvas)                 ← 上传成引擎的一张纹理/图层
  → comp.draw(...)                              ← 从这里开始与别人完全相同
  → 后处理 → 推流
```

**唯一的新工程量就是这个桥**。之后的每一步都不用改。

## 4. 两条桥接路线（建议先走 A）

| | A. 独立 context + 上传（**稳**） | B. 共用一个 GL context（**快**） |
|---|---|---|
| 做法 | `new THREE.WebGLRenderer({ canvas: offscreen })` 自己一个上下文；渲完把 canvas 用 `texImage2D` 上传进引擎的纹理 | `new THREE.WebGLRenderer({ context: animGL.ctx })`，纹理直接共享 |
| 代价 | 每帧一次 1080p 拷贝（离线渲染无所谓） | 无拷贝 |
| 风险 | 低。边界干净，两边互不知道对方 | **高**：Three.js 与引擎各自管 GL 状态（绑定、混合、viewport、VAO、program），互相污染是这类集成最经典的坑 —— **不报错，只是画面诡异**（和 `docs/STATUS.md` §13.4 那三个"静默失效"同一类） |
| 建议 | ✅ **先做这个**，把链路跑通 | 要追性能时再考虑，并且必须配一个"状态隔离"的量具 |

## 5. 必须处理的四件引擎约定（都会静默出问题）

1. **铺满整帧，并让引擎记上账。**
   引擎靠 `gl._notePaint()` 记账（`src/core/gl.js`）：**非 blend、非 `noFull` 的整帧绘制**才记进
   `paint.full`；`Pass` 默认会记，`noFull = true` 是显式退出（NV12 的 Y 平面 pass 就这么退的）。
   Three.js 那一笔必须让它记账 —— 否则 `check` 的**背景守门**会点名那一段"没铺整帧背景"。

2. **运动模糊 = 多子帧求平均。**
   静止帧 8 个子帧、普通运镜 24、甩镜/砸字最多 216。所以**同一输出帧里你的场景会被调用多次**
   （每次 `t` 略不同）⇒ Three.js 每子帧都要重渲一遍。离线可接受，但要心里有数。

3. **必须可任意 seek。**
   引擎会正着渲、倒着渲、跳着渲（`anim determinism` / `anim probe` 就是测这个）。
   场景必须能从**任意 `t` 直接**渲染出来，**绝不能依赖"上一帧"**。

4. **确定性铁律（`AGENTS.md` §4）一条都不能破。**
   不用 `Math.random()` / `Date.now()` / `performance.now()`；位置写成 `t` 的函数，不做逐帧累积；
   需要随机就 `rng(seed)` 并在 `setup` 里预计算。
   ⚠ **Three.js 本身不是不确定的** —— 只要你也这么写，它就是确定性的。别把"用了 Three.js"当成破例的理由。

## 6. 转场：用户那个直觉是对的，而且可以更省

用户自己提的"用同一个易实现且表现相同的画面做转场"是**正确方向**，可以推到底：

> **过渡镜头干脆完全用 `anim` 自己的引擎画，Three.js 只管它自己镜头内部的画面。**

这样两侧的像素风格是**同一个渲染器出的**，天然一致，不存在"对齐两套材质/光照"的问题。可做的桥：

- 纯图形过渡：扫描线扫过 / 网格扩张 / **线框"长"出实体块**（正好呼应这支片子的语言）
- 或者用引擎现成的转场机制：`overlap`（交叉溶解）或 `handlesTransition: true`（自己接管，例如甩镜）

⚠ **别用交叉溶解直接叠一个线稿镜头和一个 PBR 镜头** —— 那是风格冲突最明显的地方
（同 `AGENTS.md` §4.5 "文字量大的画面不要用交叉溶解"的道理）。

## 11. 上一轮（sodium）踩到的坑 —— 按"会不会咬到你"排序

> 详细版在 `docs/STATUS.md` §18。这里只挑**下一个会话大概率还会碰到**的。

### 11.1 🔴 排序/记账用的深度，不能拿去算线宽（我引入的，最贵的一个）

**症状**：某一段画面**整屏糊白**、亮度是别处的 5 倍（实测 YAVG 131 vs 周围 35–50），
后处理关掉也一样。

**根因**：为了让一整节的线与面共用一个排序深度，我把 `seg3` 的 `w` 换成了 `opts.dw`；
可这个 `w` **同时**还被用来算线宽，而

```js
depthScale(cam, w, H) = cam.focal / Math.max(1e-6, w) / H
```

相机**身后**的东西 `w < 0`，被 `max(1e-6, …)` 当成 1e-6 ⇒ 线宽 = `wWorld × focal / 1e-6 / H` ≈ **上亿像素**的胶囊
⇒ 几条线糊满整屏。原来的代码没事，是因为 `clipSegment(A, B, 0.15)` 把端点夹到近平面，
`w` **恒 ≥ 0.15** —— `opts.dw` 绕过了裁剪，也就绕过了那个隐含保护。

**修法**：排序用 `dw`、**线宽用裁剪之后的 `wSeg`**（已写进 `AGENTS.md` §5.5）。
另外给"实心排线的宽度"加了 420px 上限 —— 相机贴在面上时投影间距同样会炸。

**怎么定位的（这套流程值得复用）**：
关 post（`bloom/halation/vignette/ca` 全 0）→ 仍 137 ⇒ 与后处理无关；
关掉 solid 排线 → 仍 130.8 ⇒ 与半实心面无关；
关掉深度排序 → 仍 130.6 ⇒ 与排序无关；
**换回改动前的原文**（`out/_staging/orig/_world.js`）→ 31.0 ⇒ 确认是自己的改动；
再把该帧的亮度打成 **ASCII 热力图** → 看出是**整屏均匀**而不是某块区域 ⇒ 指向"一条巨大的线"。

⚠ 这个仓库**不是 git 仓库**，没有 `git diff` / 回滚。**动全局文件之前先 `Copy-Item` 一份到 `out/_staging/orig/`**
（这一轮就是靠它才定的案）。

### 11.2 🟠 `hashes --save` 对长片子会崩（已修，但你要知道边界）

**症状**：`✗ RangeError: Invalid string length`，位置在 `cmdHashes` 的 `JSON.stringify`。

**根因**：基线是**一个 JSON 文件**，每帧存"整帧像素 delta 后的 base64"（1920×1080 ≈ 7.9MB/帧），
而 `JSON.stringify` 要先在内存里拼出**一个字符串** —— V8 单个字符串上限约 512MB。
sodium 246s、`--every 4` 采 62 帧，攒到第 34 帧就 369MB。**而且写出来也没用**：
`--baseline` 那侧 `readFileSync` + `JSON.parse` 一样读不回来。

**修法**（已落地）：采样循环里记 `b64Total`，攒到 380MB 就 `die()` 并打印**这一轮真正能用的参数**。

**给下一个会话的实用口径**：长片子请用 `--times` 挑**每段的中间时刻**，别用 `--every` 均匀铺。
sodium 现在的基线就是 12 个中段时刻（`out/sodium/hashes.json`，126.6 MB，12/12 帧 `max 0`）。

### 11.3 🟠 `check` 的三点采样会"差一点就漏掉"

这一轮那个糊白帧，`check` 采的三点里**恰好有一个落在横穿世界那 4 秒里**（t=49.20）才被抓到。
**换一支片子就可能正好绕开。**

⇒ 两类问题两套量具，都不能省：
- **"整屏糊白 / 全黑 / 非有限值"** → `check` 的亮度统计能抓；
- **"画面杂乱、读不懂"** → **只能靠人眼看图**（这一轮用户点名的两处，亮度统计完全正常）。

另外那条横穿世界的 4 秒，我是**事后**才逐帧扫亮度的（40–54s 共 13 个点）。
**改动涉及"相机穿过几何体"时，主动扫一遍那一段的逐帧亮度**，别只信三个采样点。

**唯一被实测挡住的是 `out/**`** —— 并发子代理的产出先落 `out/_staging/`，渲染完再搬进仓库。

这一轮全程遵守：79 分钟的渲染里只做了**读**和往 `out/_staging/` 写字。

### 11.7 🟡 两个老坑，这轮没踩但你要知道

- **`--only` 会把选中的段平移到时间轴开头**，而 `camAt(f.t)` 用的是**整片绝对时间**
  ⇒ 核对单镜必须用 `still <任务> -t <整片绝对秒>`，用 `--only` 会得到机位错的图。
- **`video --segments N` 的 N 是"目标块时长（秒）"**，不是块数。切点只落在段边界、已渲好的块会跳过。
  指纹（`out/<任务>/<任务>.parts/params.json`）**整轮跑完才写** —— 中途 kill 掉 = 下次全部重渲。

### 11.8 时间预算（本机实测，1080p60）

| 动作 | 实测 |
|---|---|
| `still`（单帧，`--samples 1`） | 0.2–0.4 s |
| `check`（12 段 × 3 点 × 2 路径 = 72 帧） | 37 s |
| `video --samples 8 --segments 8`（246s / 14760 帧） | **4744 s ≈ 79 分钟**（3.04 fps） |
| `video --samples auto`（24 子帧）同片 | 预估 218 分钟 |
| `verify`（26 个时刻抽帧 vs 重渲） | 10–20 分钟（要在大 mp4 里逐个 seek） |
| 烧字幕重编码（x264 medium CRF 21） | 7 分 18 秒 |
| `hashes --times 12 个时刻 --save` | 约 40 s |
