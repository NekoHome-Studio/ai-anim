# FACTS.md 模板 —— 对外材料的事实出处

> **什么时候要写这份**：片子代表**某个团队 / 某个项目**对外发声时（介绍片、宣传片、发布视频）。
> 这时候每一句文案都是一次"代表他们说话"，写错了比画面难看严重得多。
>
> 做法只有一条：**宁可留空，也不许编造或推测**。写不出出处的句子，就不要放进片子。
>
> 这份模板已经被连续两支片子用过（`tasks/nekohome/FACTS.md`、`tasks/fidus/FACTS.md`），
> 它是刚需而不是仪式：上一次它直接逼出了「用户给的矩阵表和仓库 `docs/spec.md` §2.1 对不上」
> 这个**必须发问才能定**的问题（`docs/IMPROVEMENTS.md` §4）。
>
> 用法：`cp docs/FACTS-TEMPLATE.md tasks/<任务>/FACTS.md` 然后逐节填。

## 1. 逐句标出处

片子里的每一句话、每一个数字都进这张表。**出处写原文**（不是"README 里说过"），
方便下一个人核对，也方便看出"这句话到底是原文还是我概括的"。

| 片中说法 | 出处（原文，含文件/章节） |
|---|---|
| | |
| | |
| | |

**注意区分三种情况**（写清楚，别混）：

| 类型 | 写法 |
|---|---|
| **逐字引用** | 出处直接抄原文，片上引号内一字不改 |
| **概括** | 注明「据 X 概括」，并写清省略了什么 |
| **示意 / 演示画面** | 它本来就是"画的"，不是数据 —— 见 §3 |

---

## 2. 刻意没写的东西及原因（**这一节和 §1 一样重要**）

没写的东西往往比写了的东西更能说明这份材料是否可信。逐条写：为什么不写。

| 没写的内容 | 为什么 |
|---|---|
| （例）性能数字 | 官方文档没有给出可复现的 benchmark，写任何数字都是编 |
| （例）"由 X 团队开发" | 仓库公开文档里没有出现该团队名 —— 署名口径需要作者确认，不能自行推定 |
| （例）路线图里的未发布功能 | 属于规划而非事实，写进"现在时"的介绍片会误导 |
| | |

## 3. 画面里哪些是示意（不是数据）

介绍片常用"示意动画"表达抽象概念 —— 这没问题，但**必须自己标注清楚**，
否则观众会把示意图当实测图。

| 镜头 | 画面内容 | 性质 | 说明 |
|---|---|---|---|
| （例）镜头 05 | 坐标轴与网格动画 | 示意 | 用于表达"解算"这一动作，不是任何一次实测的截图 |
| （例）镜头 07 | 延迟条长度 | 示意 | 长度与真实延迟无对应关系 |
| | | | |

## 5. 引用格式（片上/文案里怎么标）

- 引用原文时用引号，且**不加修饰词**（"业界领先""革命性"这类词一律不要，除非原文就有）。
- 数字必须带限定条件（哪台机器、哪个版本、什么环境）。「42 份协议 XML」这种读数要写清
  "是那次本机实测"，不能说成"协议总数"。
- 片尾署名、团队名、致谢名单按 §2 与 §4 的结论写。
