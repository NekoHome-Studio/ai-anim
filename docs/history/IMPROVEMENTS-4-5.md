### 1. 阻断级：`--segments` 的收尾封装会**静默截掉视频尾巴** ★ ✅ **已修**

#### 1.1 现象

分块出片跑完 35 块（每块都被 CLI 用 ffprobe 逐块复核通过），最后一步报：

```
✗ 产物验收不通过，已删除 out\optifine\optifine.mp4：
  · out\optifine\optifine.mp4：ffprobe 数出 15237 帧，期望 15240 帧（差 -3）
  各块本身都通过了守门，所以问题在拼接/封装这一步。已渲好的块会保留，修完重跑即可。
```

**重跑一次，还是 −3。** 不是偶发。

#### 1.2 根因（已定位到行）

| 文件 | 期望 | 实际 |
|---|---|---|
| `out/optifine/optifine.parts/_stitched.mp4`（纯视频拼接） | 15,240 | **15,240 ✓** |
| `out/optifine/optifine.mp4`（再过一遍"封装音轨"） | 15,240 | **15,237 ✗** |

`scripts/anim.mjs` **2313–2319 行**，把音轨封装进去那一步：

```js
await runFfmpeg([
  '-y', '-loglevel', 'error',
  '-i', stitched, '-ss', String(from), '-i', audioFile,
  '-map', '0:v:0', '-map', '1:a:0',
  '-c:v', 'copy', '-c:a', 'aac', '-b:a', '320k', '-shortest',   // ← 2317 行，元凶
  '-movflags', '+faststart', out,
]);
```

`-shortest` 让 ffmpeg 在**容器时长口径**上取两路里短的那条。音轨是 254.000s、视频也是
254.000s，看似相等，但 AAC 封装有 priming samples / 尾部 padding，音频流的记账时长
比视频**短几十毫秒** → 直接被当成"短的"，把视频尾巴切掉 3 帧。

#### 1.3 为什么这条最值得修

- **它自己报错、但自己修不了**：CLI 已经明确知道"帧数不对"，却把产物删了就退出，
  用户唯一的出路是**手工绕**（下面这条），或者干脆放弃 `--segments`。
- **上一轮已经被它咬过，但被误判成偶发**：`tasks/sodium/HANDOFF.md` 第 9 条写的是
  「成片封装偶发差 1 帧（14759/14760，第一次就遇到了）：**直接重跑同一条命令**……
  第二次就过」。同一条命令、同一个根因，只是**差多少取决于音轨尾部的静音长度**，
  sodium 那次运气好重跑"过"了（其实是那一次的容器记账刚好没截）。
- `-shortest` 在这里本来就没有用：视频长度是**确定的**（`from`/`to` 与 fps 都已知），
  音轨是引擎自己按同一时间轴混出来的，不存在"哪条更长"的不确定性。

#### 1.4 修法（2026-10 已落地并验证）

**不是简单地把 `-shortest` 删掉** —— 它在这里是有用的：用 `--from/--to` 只渲一段时，
`-ss` 之后的音轨通常**比视频长**，没有它就会多出一截"只有声音没有画面"的尾巴。
正确做法是让**视频当唯一的长短基准**：`apad` 把音轨补成无限长（补的是静音），
于是 `-shortest` 必然停在视频的最后一帧上。两个方向都对：**音轨短了被补齐、长了被切掉、
而视频一帧都不会丢。**

```js
// scripts/anim.mjs · renderSegments() 的音轨封装
'-c:v', 'copy', '-c:a', 'aac', '-b:a', '320k',
'-af', 'apad', '-shortest',          // ← 这两条必须成对出现
'-movflags', '+faststart', out,
```

**验证**（复用已渲好的 35 块，只重做拼接与封装，**32.0 秒**）：

```
✓ out\optifine\optifine.mp4
  15240 帧（35 块拼接，ffprobe 复核通过），用时 32.0s
  文件大小 5762.1 MB
```

修之前同一条命令报的是「ffprobe 数出 15237 帧，期望 15240 帧（差 -3）」并删掉产物。
`anim verify optifine` 随后 **28/28 一致**。

#### 1.5 给"产物守门"的一句话建议（未落地）

守门失败时**不要把 CLI 自己也无法修复的原因写成"重跑即可"** —— 这句话这一轮把排查
方向指偏了一次（照着重跑了一遍，白等 30 秒，还是 −3）。建议按**已知/未知**分开措辞：
拼接这一步的失败是**确定性**的，重跑没有意义。

### 2. 静默失败：`css(col(P, name, a))` 里的 alpha 被丢掉

#### 2.1 现象

所有"文字淡入"**完全不生效**：段标签从第 0 帧就满不透明地画出来，
正好落在段头 0.5s 的交叉溶解区里 —— 两屏标签叠在同一位置糊成一团。

#### 2.2 根因

`src/core/util.js` **292 行**：

```js
export function css(linear, alpha = 1) {
  const [r, g, b] = linear.map(...);      // ← 只读前三量，第 4 个分量**静默丢弃**
  return alpha >= 1 ? `rgb(${r},${g},${b})` : `rgba(${r},${g},${b},${alpha})`;
}
```

而任务侧那套颜色的惯用写法是「`col()` 返回带 alpha 的四元组，直接喂给 `css()`」：

```js
col(P, name, a)  →  [r, g, b, a]        // 给 lines 用，第 4 分量是真 alpha
css(col(P, name, a))                     // ✗ alpha 被丢掉，永远是 rgb()
css(col(P, name), a)                     // ✓ 正确写法
```

**两种写法看起来只差一个括号位置，结果一个生效一个不生效，而且不报错。**

#### 2.3 证据

写 `cull`/`hd`/`natural` 的子代理用**已渲的两张图**实测对比：
同一句 `caption`，在 `alpha=0.66` 与 `alpha=1` 两个时刻，**墨色完全一样**
（最亮 0.935 / >0.7 的像素 10145 vs 10153）。

#### 2.4 本轮怎么处理的

任务侧 13 处全部改成两参数写法（`css(col(P, name), a)`），并写了一个括号配对的
批量修补脚本（不是正则 —— `col()` 的第二个参数里有 `??` 和三目）。已在
`tasks/optifine/scenes/_world.js` 的注释里点名这条。

#### 2.5 建议

| # | 建议 | 类型 | 为什么值得 |
|---|---|---|---|
| **A** | `css(linear, alpha)` 在 `linear.length >= 4 && alpha === 1` 时**取第 4 分量**当 alpha | 引擎 API | 让两种写法都对。这是一次"猜意图"的改动，但对 4 元组来说意图是明确的（它本来就叫 rgba） |
| **B** | 或者反过来：`css()` 遇到 4 元组时**抛错**，并在错误信息里直接给正确写法 | 引擎 API | 静默失败变显式失败。代价是所有老任务要跑一遍才知道 |
| **C** | `check` 的静态扫描加一条：`css(col(` 出现三参数形式就报警 | 工具 | 与现有的 `Math.random`/`Date.now` 静态拦截同一层，零行为风险 |
| **D** | `docs/ENGINE.md` / `AGENTS.md` 的颜色那一节，把「`lines` 吃四元组、`css()` 只吃两个参数」写成一行对照表 | 文档 | 本次三条里最便宜的一条 |

> 本轮**没有直接改 `src/core/util.js`**（仓库口径：片子只写在 `tasks/` 下），只提建议 + 证据。

### 3. 渲染期写文件 → `check` 报一句看不懂的 `TypeError`

#### 3.1 现象

`anim check optifine` 跑到第 4 段（`multicore` 的第三个采样点）之后直接崩：

```
  multicore      t=70.00s  单帧 0.137  多子帧 0.138（24 子帧）
node : ✗ page.evaluate: TypeError: Cannot read properties of undefined (reading 'stats')
    at statsAt (D:\ai动画\scripts\anim.mjs:864:47)
    at cmdCheck (D:\ai动画\scripts\anim.mjs:893:27)
```

**报错信息里没有一个字提到"文件被改了"或"页面重载了"。**

#### 3.2 根因

并发跑的第三路子代理在 **19:45:21** 重写了 `tasks/optifine/scenes/deferred.js`。
私有 Vite 的 HMR 收到变更 → 整页重载 → 页面里那个装着引擎状态的全局对象没了 →

#### 3.3 为什么值得改

`AGENTS.md` §7 已经把规则写得很清楚了（「**只要有一场渲染在跑，就一个文件都别写**」，
还专门注明"**开渲之前先让所有子代理停手**"）。问题**不在规则缺失，而在违反规则的代价

这一轮为此白跑了一轮 40 秒的 `check`，并且差点误判成"某个场景写出了 NaN"。

#### 4.2 那个 bug 值得单独说：`facesToward()` 判据反了

```js
// 老代码（两份 _world.js 都一样）
const px = 面心[0] - cam.pos[0]; ...
```

2. 于是每个盒子**只画背对镜头的三个面**，整片世界读成一块**半透明水晶**，而不是一叠积木
   —— 用户的原话「各种建模可能有点杂乱，而且不清楚，不够直观」就是这个。

> 这个 bug **不是引擎的**（它在任务侧的 `_world.js` 里），但它是"引擎缺一层"的直接证据：
> 公共知识写在某个任务的私有文件里，就会被抄错、而且抄错两次。

#### 4.3 配套的一条视觉规律：**"压暗"不能用"变透明"**

修好 `facesToward` 之后世界**仍然**像玻璃，第二层原因是：

- `LineBatch` 没有深度测试，面的"填充"是**一排线**拼出来的（`hatchQuad({solid:true})`）；
- 只要 `alpha < 1`，排线之间那道发丝缝就会把**后面的节**透出来；
- 于是"把背景那 17 节压暗"如果写成"把 alpha 降到 0.4"，得到的是"把整片世界变成玻璃"。

正确做法（本轮的 `drawSection`）：

```js
// 填充：只有 a < 0.17 才真的淡出（那是给"出现/消失"用的）
const fillA = sat((a - 0.05) / 0.12) * smoothstep(9, 26, dl) * fillK;
// "暗"由**颜色**承担：tone 随 a 线性掉到 0.22
const tint = base * (0.22 + 0.78 * a);
// 排线缝闭死
hatchQuad(..., { solid: true, solidK: 0.99, minW: 1.6 });
```

一句话：**alpha 管"在不在"，tone 管"亮不亮"。** 建议写进 `docs/COOKBOOK.md`。

### 5. 子代理协作：本轮跑得最好的一条（建议固化成模板）

#### 5.1 做法

11 个场景文件（`three` `chunk` `multicore` `cull` `hd` `natural` `cem` `deferred` `composite` `shadow` `outro`）
**并行分给 4 个子代理**，每个 2–4 个文件。主代理只先写好两个"风格钉死"的参考场景
（`hook` = 3D 范本、`ctm` = 2D 面板范本）和一份 **`out/_staging/SCENE-BRIEF.md`**（写作规范）。

#### 5.2 结果

- 11 个文件**一次通过率很高**：主代理只做了 3 处修正
  （`three` 的面板底色太重、`chunk` 的机位太近、`multicore` 的 `3×` 压住标题）；

### 1. 「视频风格被定死」：根因审计

只读审计（不写文件、不跑渲染）的结论，按权重排：

#### 1.1 主因：8 个镜头模板是**两支旧片子的逐像素冻结副本**

`src/shots/*.js` 的绘制代码是从 `tasks/demo/scenes/` 与 `tasks/beat/scenes/` **逐字搬过来的**
（`docs/STATUS.md` §1635：「数值、运算顺序、绘制顺序、Pass 的 shader 源码与 key、每条注释都原样保留」），
验收判据是 `anim hashes demo --baseline` **零像素差**。于是：

- 每个模板文件头都写着「⚠ 改这里的任何数值或绘制顺序都会改变已有任务的画面」；
- 模板默认值就是 demo 的文案（「ANIM / CODE-RENDERED MOTION」「每次迭代的最高准确率」）；
- 8/8 模板 `return` 的 post 里都锁着 `bloom` + `halation` + `grain`；
- 8/8 模板硬编码 `family: 'sans' | 'mono'`，**0 个颜色参数、0 个字体参数、0 个版面参数**。

#### 1.2 强放大器：交付流程照抄同一份 SCENE-BRIEF

`out/_staging/SCENE-BRIEF.md:92` 原文是「视觉语言（全片统一，**照这个来，不要自创**）」，
`:105-121` 钉死版面栅格与字号，`:65` 钉死 `{ bloom: 0.32, grain: 0.02, vignette: 0.5, ca: 0.1 }`。
更早的证据：`tasks/sodium/narration.mjs` 与 `tasks/optifine/narration.mjs` 的
`VOICE` / `RATE` / `TAIL` / `MAX_STRETCH` / `BPM` **连中文注释都逐字相同** —— 第二支片子抄了第一支。

#### 1.3 三个隐形钉死源

| 源 | 事实 |
|---|---|
| 默认调色板就是一支旧片子的配色 | `src/core/palette.js` 的注释自认「默认是 **pdoom** 那种印刷品配色」，而 `tasks/pdoom-lab/task.config.mjs` 列的 hex 与它**逐一相同** |
| **字体全引擎回退** | `public/fonts/` 只装了 `Manrope-600.woff2`，而 `FAMILIES` 的首选 `Archivo` / `IBM Plex Mono` / `Cormorant Garamond` **文件都不存在** → 每支片子都是**微软雅黑 + Consolas**。这一条没人提过，但它让"换了配色"的片子看起来仍然是同一支 |
| 引擎里没有"风格"这个概念 | `grep preset\|theme src/` 零命中；外观入口只有 `palette`(9 色) + `fonts` + 手写场景，三者互不知道 |

#### 1.4 文档惯性（引擎允许，但文档只会一种写法）

- `README.md` / `AGENTS.md` / `docs/COOKBOOK.md` 三份入口印的**是同一段起手场景**（同字号、同 post）；
- `COOKBOOK.md:1121` 的 palette 示范写的是**默认值**（`signal: '#ff4d12'`）—— 照抄等于没改；
- `COOKBOOK.md:1126` 的 post 示范写的就是 chart 模板自己 return 的值 —— 同理；
- 唯一公开示例 `tasks/example-config-only/` 明说「调色板保持默认…不引入需要肉眼再确认一遍的变量」。

**判断**：能力不足只在"纯配置出片"这条路上成立（配置档换不了背景/字体/模板 post），
而配置档恰好是文档推荐的首选路径。真正缺的是**"风格"这个一等公民**。

### 2. 落地：风格系统（style pack）

#### 2.1 新增 `src/style/index.js`

#### 2.2 三条不能破的规矩（都有回归保护）

1. **不写 `style` = `print` = 引擎从前的默认观感** —— `print` 的 `palette` / `fonts` / `post`
   都是**空对象**，`captions: false`。`tools/test-style.mjs` 前 6 条断言钉的就是这件事：
   只要有人给 `print` 加一个色值，全仓库老片子一起变。
2. **模板一行都不用改** —— 模板里所有颜色都写成 `P.xxx`、字体写成逻辑名 `family: 'sans'`，
   所以换 palette / 换字体栈它们自动跟随（`_ctxFor` 之外没有一处需要特判）。
3. **背景母题只对 `world: 'auto'` 的段生效** —— 8 个模板自带满帧背景，这是能力边界，文档写清楚了。

### 3. 「两条字幕同屏」：根因审计

#### 3.1 字幕以前不在引擎里

- 引擎只提供**排版原语**（`karaoke` / `writeLine` / `wrap`），x/y 必须调用方给，**没有默认带、没有安全区**；
- 真实交付的字幕是出锅之后用 `ffmpeg -i … -vf "ass=…" …` 烧的（`tasks/sodium/HANDOFF.md:168-172`），
  样式写死在 `out/*.ass`：`Alignment=8`（**顶部居中**）、`MarginV=34`、`Fontsize=46`；
- 生成脚本 `out/_staging/make-srt.mjs` 与 `make-optifine-srt.mjs` 是**两份近乎逐字重复的手抄脚本**，
  活在**渲染产物目录**里（`anim clean` 会清掉、不在版本管理视野内、没有任何回归）。

#### 3.2 观众到底看到了什么

逐字比对（去掉标点空白后，**字符串字面量 == 旁白整句**，注释逐字符剥离）：

| 任务 | 命中 | 说明 |
|---|---|---|
| `tasks/sodium` | **12/43 句（28%）** | 顶部字幕 + 左下说明条**同一句话**，同屏同时 |
| `tasks/optifine` | 3/47（6%） | 同上 |
| `tasks/beast` | **0/26** | 它的 `SCRIPT.md` 把「旁白」与「屏幕上写了什么」当两列写，画面只放数字/代码/出处 |

铁证帧（仓库里现成的）：`out/_staging/sub-213.png`（sodium t=213s）—— 顶部字幕
「论文里的数字：动态排序快六成。」＋ 左下说明条同一句 44px 粗体 ＋ 右下角面板「论文数字 · 非本机实测」，
**一句话同屏出现三次**。字幕 46px、说明条 44px，观感几乎一样 —— 观众当然会把说明条当成第二条字幕。

**外部依据**（不是我们的口味问题，已于 2026-10 逐条核到原文）：Netflix 的 timed-text 规范把
"与画面文字相同、或已被对白覆盖的 forced narrative"列为**必须删除**（§7），
同一份规范还给了中文字幕的硬指标：**16 字/行、最多 2 行、≤9 字/秒**（§1 / §10 / §14），
以及**连续多条字幕要整体同位、不许上下跳**（§18）—— 本引擎的字幕层就是照这几条做的。
至于"要不要给字幕加逐词高亮"：有一项对照实验研究的正是"偶尔出现的关键词"这条路线，
方向是**关键词突显对学习不利**（Cojean & Martin 2021，*L'Année psychologique* 121(4):417-442；
书目已核实、样本量未核实），所以引擎默认不做。**注意边界**：被质疑的是"字幕之上再加高亮"，
不是"字幕"本身。

### 4. 落地：字幕一等公民 + 版面分区

#### 4.1 引擎级字幕层（`src/core/captions.js`）

```js
captions: true,        // task.config.mjs —— 场景里一个字都不用写
```

- 引擎每帧自动画"此刻该说的那句"：`at(t) ?? recent(t, hold)`（说完再留 1.06s，观众还在读）；
- 折行按 **Netflix 简体中文规范**（每行 16 字、最多 2 行），底边/顶边对齐 → 句长变化时**不上下跳**；
- 画在**后处理之后**：字幕是信息层，吃泛光/颗粒会把字糊掉（"骨白正文永远不要 bloom"）；
- `karaoke` **默认关**（研究上关键词突显是负效应），要开就显式开。

#### 4.2 版面分区（`src/kit/bands.js`）

六条带：`title` / `tag` / `hudR` / `caption` / `foot` / **`sub`（字幕保留带）**。
`assertInBand(name, x, y, ctx, size, width)` 在文字压进字幕带时把警告 push 进 `ctx.warnings`
（每帧都会发生的事不能 `console.warn` 刷屏），`anim check` 会把它们打出来。

> **字幕带为什么在顶部**（反直觉，但被引擎现状逼出来的）：底部已经被占满了 ——
> 8 个模板的 `readout` / 签名 / `footer` 都在 y≈990，`footer()` 在 H-62，
> 说明条在 964/1004。往底部再塞一条字幕，就是"两块文字抢同一片区域"。
> 顶部居中（y 40–104）与左上段标签（x≥128）、右上读数（x≥1190）在**水平方向**也不重叠。
